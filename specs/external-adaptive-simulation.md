# External Adaptive Simulation Interface

Status: normative architecture extension; Section 13 implemented in source 2026-09-15; deployment qualification required
Schema families: native resources v1alpha1; delivery capabilities and Operations requests v1alpha2
Date: 2026-09-13

## 1. Purpose

This document specifies Interceptor Sandbox enhancements needed for reliable
adaptive attack simulation. The interfaces are producer-neutral:

- Operator Sandbox can use them to execute an AEF ScenarioBundle;
- PromptFoo or another harness can use them without AEF or Operator;
- AEF can consume capability and post-run evidence resources without becoming
  an Interceptor runtime dependency.

Interceptor remains a simple, independently useful open-source execution and
evidence environment. It does not generate payloads, run an attack-planning
loop, or interpret AEF technique objects.

The IDs are retained for traceability even though `AEF` in an ID no longer
means the feature is proprietary or AEF-specific.

## 2. Updated interaction model

```text
planning:
Interceptor CapabilityManifest -> AEF or another planner

execution:
external engine -> producer-neutral AttemptContext -> Interceptor operation
                <- target response + permitted ObservationView

post-run proprietary product:
Operator CampaignExecutionBundle + Interceptor EvidenceBundle(s) -> AEF assessment
```

The external attack engine crafts the concrete payload. AEF may provide optional
scenario and technique provenance, but Interceptor validates only generic
identity, content, operation, policy, and session bindings.

During ordinary execution, the harness does not receive all information that
Interceptor records. This asymmetry is intentional. Protected evidence is
exported through a trusted post-run path and allows AEF to compare the attacker's
view with execution truth without giving the engine unfair live knowledge.

## 4. INT-AEF-AD-001 — attempt context and ancestry

### 4.1 Problem

Adaptive engines create, refine, branch, and stage attempts dynamically. Static
injection IDs alone cannot explain which generated artifact caused an
Interceptor event or how one attempt evolved from another.

### 4.2 AttemptContext

Register one immutable context before arming or executing its payload:

```json
{
  "api_version": "interceptor.dev/attempt-context/v1alpha1",
  "campaign_id": "campaign-01",
  "thread_id": "thread-01",
  "attempt_id": "attempt-0003",
  "parent_attempt_id": "attempt-0002",
  "generation": 3,
  "attempt_index": 17,
  "payload": {
    "digest": "sha256:...",
    "size_bytes": 97,
    "media_type": "application/json"
  },
  "generator": {
    "kind": "adaptive-engine",
    "release_digest": "sha256:..."
  },
  "strategy_provenance_ref": "sha256:...",
  "feedback_profile": "black-box",
  "created_at": "2026-08-31T20:00:00Z"
}
```

`strategy_provenance_ref` is optional and opaque to Interceptor. It may point to
AEF scenario/action/recipe provenance, a PromptFoo test case, or another
producer's metadata. Interceptor MUST NOT require or dereference it.

Registration requirements:

- campaign, thread, attempt, and parent relationships are bounded and stable;
- attempt IDs are unique within the session and cannot be overwritten;
- a parent must already exist in the same campaign and permitted thread graph;
- generation and attempt index are monotonic according to the session policy;
- payload descriptor matches a registered, verified artifact;
- the selected feedback profile matches immutable session policy;
- metadata cannot change routing, authorization, visibility, or safety policy.

### 4.3 Propagation

All injections, application turns, normalized events, provider-boundary
deliveries, oracle results, and artifact lifecycle records caused by an attempt
carry `attempt_id` and payload digest when known. Derived internal work preserves
causal ancestry rather than relying on timing.

Dynamic registration is bounded by attempt, artifact, byte, and rate limits.

Operator's public export and submitted-bundle references use the separate
[public capability integration](../docs/operator-capabilities.md). Preserve native
manifest identity; Operator maps allowlisted fields into its versioned schema.
Source digests record authoring provenance. Operator checks live compatibility by
default, or exact public projection equality when explicitly requested by a bundle.
This does not alter native attempt, execution or feedback enforcement.

## 5. INT-AEF-AD-002 — feedback visibility and ObservationView

### 5.1 Visibility classes

Interceptor classifies recorded facts as:

- `target_visible` — natural application output a real target user sees;
- `harness_visible` — normalized operational fact permitted to the harness;
- `operator_only` — trusted control-plane diagnostic or lifecycle fact;
- `protected` — raw evidence, oracle internals, fixture values, canaries,
  provider-boundary details, or sensitive state.

Classification occurs before serialization. A protected field is omitted, not
returned with a label that asks the caller to ignore it.

### 5.2 FeedbackProfile

Every session selects one immutable profile, initially:

- `black-box` — target-visible output and minimum operation status;
- `diagnostic` — black-box plus normalized operation errors and recorded delivery facts;
- `oracle-assisted` — diagnostic plus supported, attributed event-backed oracle outcomes,
  never raw secrets or unrestricted events.

The environment declares which profiles it supports. Operator may narrow the visible feedback but cannot broaden the active profile.
Native AttemptContext MUST retain the exact session `feedback_profile`; the
bundle's effective harness profile is a separate Operator policy. Operator sends
only the permitted selected kinds, independently projects all response fields and
receipt reads, and reports the effective profile to Attack Harness. Empty intersections skip
native feedback collection using the registration and category rules in
[Operator feedback narrowing](../docs/feedback.md#operator-feedback-narrowing).
Interceptor retains its immutable-profile equality check.

### 5.3 ObservationView and content

The normative [live feedback contract](../docs/feedback.md) defines native
`observation-view/v1alpha2`, optional AttemptContext `observation_selection`,
fixed per-invocation receipts and bounded `observation.content.read` bytes.
Omitted selection means all permitted kinds, bounded by the immutable profile;
selected subsets cannot broaden it. Selection is part of attempt identity.

Collect the exact invocation's view before cleanup/transition; do not silently
select the latest turn or regenerate old observations from current state. The
manifest accounts for all fixed categories, including withheld, unavailable and
partial feedback. Retained receipt reads preserve campaign and source-attempt
binding across target restore/stop without restarting the target. EOF, capture
truncation and collection completeness are separate. Missing oracle/delivery
facts are not negative results. Operator implements its own guest receipt mapping
and model-facing projection under the [shared contract](../../operator_sandbox/schemas/FEEDBACK_CONTRACT.md).

## 6. INT-AEF-AD-003 — capability manifest

Interceptor exports a deterministic, secret-free `CapabilityManifest` bound to
the sealed Environment and Application digests. It includes:

- manifest and Interceptor schema/release versions;
- target/application identity and supported feedback profiles;
- typed application and Operations operations;
- injection surfaces, placements, modes, selectors, carriers, and limits;
- per-target injection surfaces, creatable state collections, logical
  file-injection namespaces and their ceilings;
- managed services, native MCP servers/tools, identities, static/dynamic
  synthetic attacker services, and stateful fixtures by stable metadata ID;
- observation kinds and oracle types;
- native model-proxy codecs, host provider-adapter kinds, non-secret
  authentication-mode classes, model/deployment constraints, and feature
  flags;
- snapshot/checkpoint support;
- closed DNS policy/query ceilings and HTTP/HTTPS front-door/TLS trust
  capabilities, without private listener or certificate material;
- attempt, invocation, artifact, concurrency, and size limits.

It excludes credentials, private prompt/fixture bodies, hidden canary values,
private host/container paths, private network details, evidence, and
operator-only configuration. Explicitly reviewed public delivery examples are
allowed. Logical service paths, tool names, JSON Pointers and namespace-relative
filenames are selectors, never destination or administrative routes.

[INT-DEL-001–005](delivery-contracts.md) define v1alpha2 application delivery
contracts, opt-in service endpoint exports, uncertain MCP outputs, the named
implementation extension point and source/served-copy mutation semantics.
v1alpha1 Blueprints retain their existing manifest representation. A consumer
must support the advertised version, rather than relabeling an old fixture.

The same sealed inputs produce the same canonical manifest digest. The session binding and any AEF ScenarioBundle bind that exact digest. A changed manifest
requires revalidation and, for AEF plans, a new ScenarioBundle.

## 7. INT-AEF-AD-004 — attempt-indexed evidence export

After live harness authority closes, a trusted operator may request an
immutable `EvidenceBundle`:

```json
{
  "api_version": "interceptor.dev/evidence-bundle/v1alpha1",
  "kind": "EvidenceBundle",
  "campaign_id": "campaign-01",
  "session_id": "session-01",
  "environment_digest": "sha256:...",
  "application_digest": "sha256:...",
  "capability_manifest_digest": "sha256:...",
  "interceptor_release_digest": "sha256:...",
  "feedback_profile": "black-box",
  "completeness": {
    "state": "complete",
    "start_sequence": 1,
    "end_sequence": 902,
    "truncated": false
  },
  "attempts": [],
  "snapshots": [],
  "restores": [],
  "artifact_refs": [],
  "oracles": [],
  "injections": [],
  "coverage_gaps": [],
  "created_at": "2026-08-31T21:00:00Z"
}
```

The bundle indexes authoritative events, injection application, service/tool
results, state mutations, provider-boundary delivery, oracle results, and
causality by attempt and payload digest. Large event sets and bodies are
content-addressed artifacts.

The combined post-run record includes operation and idempotency IDs, request
origin, accepted/completed timestamps, revision effects, and ambiguity
reconciliation from Operator, plus Interceptor's authoritative snapshot ID,
digest, canonical committed size, parent snapshot, sealed environment,
application, capability and release bindings, and result. Restore records also
identify the source and resulting session lineage. Snapshot bodies are not
included in an ordinary EvidenceBundle unless an export policy explicitly
lists them as protected artifacts.

Export requires trusted host authority unavailable to the guest. The
current local interface writes a deterministic portable tar stream after
integrity verification and includes explicit completeness/truncation markers.
An orderly shutdown persists the final protected evaluation; if abnormal
termination prevents that step, export retains the verified raw record and
marks the bundle partial. Repeating an export of unchanged sealed evidence
yields the same EvidenceBundle digest.

AEF is an important downstream consumer but not the only permitted consumer.
Operator may relay the verified bundle in its FinalSubmission; Interceptor does
not call AEF directly.

## 8. INT-AEF-AD-005 — canonical payload artifact identity

The payload flow is:

1. An external engine generates concrete bytes.
2. Operator or another harness computes a declared digest and registers the
   artifact with Interceptor.
3. Interceptor streams or accepts the bounded body, verifies size, media type,
   canonicalization rule, and digest, then commits it immutably.
4. The producer registers an AttemptContext referring to that digest.
5. An injection or application operation refers to the attempt and digest.
6. Interceptor records the same verified identity through application,
   consumption, delivery, event, and evidence records.
7. Post-run consumers join Operator execution and Interceptor evidence using
   attempt ID plus payload digest.

Example descriptor:

```json
{
  "digest": "sha256:...",
  "size_bytes": 97,
  "media_type": "application/json",
  "canonicalization": "jcs-v1"
}
```

For structured payloads, the contract explicitly chooses whether the digest is
over raw bytes or a versioned canonical representation. It never silently
parses and reserializes. Non-JSON bodies use raw-byte digests. Digest, size,
canonicalization, or media-type mismatch fails before use.

This identity does not imply AEF generated the payload. The artifact may come
from Operator's engine, PromptFoo, a human-authored harness, or another tool.
Normal ObservationView returns the digest, not protected payload content.

## 9. INT-AEF-AD-006 — managed HTTP response injection

**Implementation status:** supported. Managed services expose an
attempt-attributed rewrite point after a successful handler response and before
the application consumes it.

Add `service_response` / `simulation` with this order:

1. authorize the real request;
2. execute the real fixture or stateful handler;
3. construct a normalized response candidate;
4. match service, route, ordinal, and bounded request predicates;
5. apply one typed operation—`replace`, `prepend_text`, `append_text`, or
   `merge_object`—at a JSON Pointer or UTF-8 text body;
6. record original and resulting digests plus attempt/injection identity;
7. return the modified response to the application;
8. independently record any later provider-boundary delivery.

The surface cannot change authorization decisions, identity, destination,
status, or security-sensitive headers. An authorization failure provides no
injectable response candidate. Exact method/path, bounded query/header/body
predicates, and per-definition journaled ordinals make adaptive targeting
reliable after setup traffic. A Blueprint-enabled dynamic attacker HTTP service
uses the same body-only surface after capture; a static sink rejects arming.

## 10. INT-AEF-AD-007 — native MCP result injection

**Implementation status:** supported. `mcp_tool_result` is distinct from
`model_tool_result` and operates between successful native MCP execution and
application consumption.

Add `mcp_tool_result` / `simulation` after native MCP authorization and actual
tool execution. Selectors use stable server ID, tool name, call ordinal, and
bounded scalar argument predicates. Placements and mutation operations use the
same restricted forms as managed HTTP response injection.

Evidence records real-result digest, rewritten-result digest, injection ID,
attempt ID, MCP server/tool identity, and later provider delivery when present.
The manifest reports `mcp_tool_result` and `model_tool_result` as distinct
surfaces so planners and reports make accurate fidelity claims.

### 10.1 Dynamic source completeness

The sealed Blueprint describes where adaptive payloads may be placed; it does
not contain those payloads. `environment_state` may create a missing service
record only in an explicitly opted collection with a positive ceiling and a
sealed stateful HTTP/MCP create contract that validates the complete object. A
missing file may be created only through a named logical injection namespace
with explicit permission and file-count and byte ceilings. Absolute file paths
remain update-only.

A Blueprint MAY declare multiple attacker HTTP services. Static responses are
capture-only exfiltration sinks. Dynamic responses reuse `service_response`
after capture and provide bounded request/response C2 simulation without adding
a generic proxy or unrestricted tasking channel.

Local command execution is not a syscall-interposition surface. `curl` and
similar clients receive injected bytes when they call a declared injectable
HTTP service; command output later represented as a client tool result is
covered by `model_tool_result`. The manifest MUST NOT claim interception of
arbitrary descendant stdout or undeclared localhost communication.

## 11. INT-AEF-AD-008 — checkpoint fork convenience

**Implementation status:** deliberately deferred. Compose the existing
Operator-controlled snapshot and trusted host restore operations unless
measurements demonstrate that an additional atomic primitive is necessary.

The baseline Operations interface exposes narrow Operator-controlled live
`snapshot.create`; restore remains an existing host control-plane operation
because it creates a fresh Interceptor session. Add an optional atomic
convenience operation that quiesces and checkpoints a
session, creates named children, attaches distinct thread contexts, preserves a
common parent checkpoint, and applies the same snapshot limits and safety
checks.

The fork convenience remains deliberately marginal. A trusted external
orchestrator can implement the same sequence using the narrow primitives. The
attack-engine process never receives an Interceptor administrative credential
or unrestricted restore authority. It may make a typed request to Operator,
but Operator decides whether and when to issue the actual Interceptor mutation.

## 12. INT-AEF-AD-009 — typed event-match oracle

Add a bounded deterministic `event_match` oracle for effects already represented
as normalized events. Filters may include exact channel, layer, kind,
attempt/injection identity, and provenance values. Top-level semantic fields,
including normalized operations, use bounded scalar predicates:

- `equals`
- `contains`
- `exists`
- `one_of`

Do not support scripts, regular expressions, arbitrary JSONPath, callbacks, or
user-selected code. Results include bounded count, first matching event sequence
and digest, visibility, and causality state. Causality is confirmed only through
explicit attempt/injection provenance, never time proximity alone.

Raw oracle details remain protected unless an immutable oracle-assisted profile
expressly exposes a normalized result.

## 13. INT-AEF-AD-010 — Operations interface

### 13.1 Boundary

Operator and Interceptor run on the same trusted host. `interceptor run` starts
one target container and the integrated API at `127.0.0.1:8080`. There is no
separate gateway process, integration token, TLS or remote provisioner in this
MVP. The network-disabled engine guest talks only to Operator's typed non-network
broker. It receives no Interceptor private bridge, Docker socket, provider
credential, host data root or protected evidence. Model-provider credential
handling remains unchanged.

The normative [local integration contract](../docs/local-api.md) defines startup,
attachment, routes, restore, stop, evidence, request limits and failure behavior.
Evidence archives use the configured per-session export limit (default 4 GiB),
advertised as `evidence_max_bytes` on attach/status. The limit covers generated tar
bytes as well as transfer. Oversize exports preserve retained sources and return
an explicit collection gap; administrative export with a larger limit can support
later reporting without campaign replay. Operator accounts these host-only archives
separately from harness artifact/read budgets and verifies full size/digest.
AEF supplies immutable inputs and receives finalized bundles; it is not a live
caller. All host users who can reach loopback are trusted in this MVP.

### 13.2 Session identity and campaign access

The first `/v1/attach` binds the service instance to one campaign and returns the
current native session ID, capabilities, lifecycle revision and caller attribution.
Same-campaign attachment with the same stop policy is idempotent; another campaign
is rejected for the entire instance lifetime. Session IDs and binding fields are
correlation data, not credentials. The service associates each native session with one campaign using the v1alpha2
supervisor contract. Principal records internal service identity, not caller authority. `allow_target_stop` is immutable, defaults false, and records Operator's
explicit final target-shutdown choice.

Operator uses the current session and supplies its own worker/revision attribution
in native experiment requests. The
supervisor retains durable request deduplication, expected-revision checks,
campaign access, native budgets and permanent per-session closure. The
integrated service additionally rejects stale-session mutations before forwarding.
Planned restore closes/removes the source, starts a fresh session, binds the same
campaign and advances the native run revision once on success. No containers
overlap. Explicit restore authorizes source replacement independently of optional
final-stop permission.

Public `session.owner` accepts `close_execution` only; binding uses attachment.
An explicit close is terminal for this campaign, bypasses pending mutation work,
and prevents later restore. Already-dispatched effects may finish. Campaign-scoped
injection cleanup and permitted stop remain available. A planned healthy restore
uses the lifecycle operation rather than terminal campaign closure. Restored
attempt registries retain campaign provenance. No process restart or ownership
transfer resumes a failed campaign.

Native execution closure is also terminal for the campaign. After each forwarded
mutation, the integrated API reconciles authoritative native execution state;
uncertain mutation responses or transport failures close admission conservatively.
It persists the instance ledger's `closed` flag before releasing the mutation gate
or returning the result. If that persistence fails, in-memory closure and the
ledger-failure latch still block mutations and restore. Known rejections do not
close an otherwise healthy campaign. Status reads, exact owned injection cleanup
and opted-in final stop remain available subject to existing failure checks.

The host MUST also report independent execution failure without waiting for another
Operator request. Its existing 500 ms health loop checks native terminal metadata
and container state; native errors such as `WALL_TIME_LIMIT` close admission even
while the supervisor is still shutting down. Unexpected target exit and model
connector failure do the same. A final notification check on every runtime return
covers startup/early-return paths before that run is declared finished.

Persist `phase: "error"`, `closed: true` and a `failure` object containing
`session_id`, `reason`, and UTC `observed_at` in the instance ledger. Return the same
object from lifecycle `POST /v1/status`; it is null until a failure is recorded.
Preserve the first recorded reason/time, including the supervisor's specific reason;
later cleanup errors must not replace it. These fields describe execution failure,
not confirmed container removal or the outcome of an interrupted native operation.
Close admission in memory before ledger persistence, bypass the mutation gate, and
report `store_available: false` on write failure. Docker termination must proceed
independently of the notification/persistence path. Retain uncertain in-flight
outcomes; existing successful receipts remain successful.

Mark a requested stop/restore shutdown before initiating target termination. A clean
planned source exit keeps restore transitioning; a clean final stop yields stopped
and closed. Explicit native errors and cleanup failures take precedence over the
planned marker. Merely being in restore preflight is not a planned shutdown. Scope
callbacks to the actual target run: a delayed old-run callback cannot close a
replacement, while failure of a replacement not yet published in the API binding
must close execution. Latch failures arriving before API initialization as well.
Preflight rejection, replacement binding and final-stop completion MUST NOT overwrite
a latched failure with ready/stopped status. Healthy restore and rejected healthy
preflight retain their existing behavior. No extra service, push channel or restart
mechanism is required.

Before a restore closes or stops the source, the integrated handler independently
queries native `session.status` under the mutation gate. It requires the matching
session/campaign association, open execution and running target; a cached `closed: false`
or a running container alone is insufficient. Closed, unavailable or malformed
native state rejects restore and closes campaign admission without replacing the
target. The subsequent native close acknowledgement must confirm planned
controller closure, not an earlier fault closure. Rejection never starts a new
session or advances the run revision. These checks live in the existing Interceptor
process; they introduce no separate lifecycle service or recovery mechanism.

Campaign ID is the access boundary. Worker ID and campaign run revision are
required attribution on native operation requests, not permission requirements;
a different worker or revision of the same campaign may interact with the current
target and read retained campaign sessions. The internal service principal is
provenance, not an exclusive owner. Historical `session.owner`/`owner` names remain
wire labels for campaign association, stop policy and terminal closure.
They do not establish worker ownership or require transfers after restore.

Injection cleanup accepts any existing injection in the addressed campaign session,
including checkpoint-restored injections with no arm record in the new execution
store. Confirmed missing injections return `404 not_found`; persistence/journal
failures return `500 injection_delete_failed`, never a false not-found result.
Operator's `engine.injection_delete` resolves a known campaign attempt-receipt/action
handle to the native ID and sends the deletion to its current target binding.
It may normalize only a confirmed missing injection for that exact operation to
successful `already_absent` cleanup. Unknown host handles or transport/session
errors cannot be normalized. The request needs no original arm record or attempt
context. Worker/revision remain attribution, not resource ownership. Old cleanup
records cannot prove absence after a restore that resurrects the injection.
Removing an injection does not roll back its previous target effects.
See the [shared cleanup contract](../../operator_sandbox/schemas/INJECTION_CLEANUP_CONTRACT.md). Duplicate injection IDs cannot overwrite
existing definitions; use a fresh ID or delete before reusing an ID. Mutated payloads
use new operation IDs. Native expected-session-revision checks, current-target
addressing, closure, visibility, budgets and stop opt-in remain in force.

Duplicate-effect comparison excludes worker/revision attribution, including the
legacy worker field in a `session.owner` body. The full original request and its
fingerprint remain immutable audit data; a retry returns the original result and
never overwrites the originating caller. Other request fields/command bytes remain
fixed for an exact retry, including target, operation ID, request ID, deadline and
expected native revision. A new worker can also query `operation.status` without
copying the original request. Lifecycle duplicate comparison likewise excludes
caller attribution while preserving the admitted request in its ledger.

Attach requires Operator `worker_instance_id`; lifecycle restore/stop requests
require `worker_instance_id` and positive `run_revision` as audit metadata. These
do not control the server-maintained lifecycle sequence.

### 13.3 Operation records and request handling

The envelope is `interceptor.dev/operation-request/v1alpha2`; the public body
contains `request` (shown below) and `body` (the closed operation body). Native
codecs/fixtures and the detailed wire guide define its representation:

```json
{
  "api_version": "interceptor.dev/operation-request/v1alpha2",
  "request_id": "request-01",
  "operation_id": "operation-0003-invoke",
  "operation": "application.invoke",
  "session_id": "session-approved",
  "campaign_id": "campaign-01",
  "worker_instance_id": "operator-worker-01",
  "run_revision": 1,
  "expected_session_revision": 42,
  "attempt_id": "attempt-0003",
  "attempt_context_digest": "sha256:...",
  "body_digest": "sha256:...",
  "deadline": "2026-09-14T21:00:00Z"
}
```

Operator records the exact command, correlation IDs, native receipts, result or
uncertainty and resource charges in its durable campaign journal. Interceptor
preserves its existing event recording, state journals, attempt/artifact registry,
evaluation and evidence export. These establish what happened and what remains
unknown for reporting; they are not instructions to resume a failed campaign.
Private native/protected records never become live harness context.

Within a live execution, keep bounded duplicate-request suppression and mutation
serialization. The same request/operation identity with different command bytes
or target/campaign bindings is a conflict (worker/revision attribution is excluded); concurrent duplicates cannot create a second effect.
Return an already-known result or in-progress indication when available. Capacity
exhaustion rejects new work before effects rather than evicting active duplicate
protection. A lost reply or unavailable lookup is not proof of non-execution.
Operator reconciles transport loss through read-only operation lookup within
bounded recovery deadlines. It does not resubmit an uncertain mutation as a new
operation or continue failed execution.

`operation.status` accepts exactly one of `receipt_id` (the existing native
application-turn lookup) or `operation_id` (the durable mutation record).
Historical reporting uses retained native recording and
evidence export, with explicit partial/missing outcomes when a result is absent.
Status inspection and export do not start the target or grant execution authority.
The source includes native request/result codecs and compatibility fixtures.
See the wire guide for bounded retention and journal-integrity behavior.

### 13.4 Initial operation surface

The integrated local service provides `POST /v1/operations` without integration
authentication. Host-owned `session.owner` is never derived from an engine operation.

| Operation | Purpose |
|---|---|
| `session.owner` | Irreversibly close execution; `/v1/attach` performs native binding internally. |
| `session.status` | Available native lifecycle/revision/limits plus the bound owner and execution-closed state. |
| `operation.status` | Lookup by `receipt_id` while native turn status is available, or durable mutation lookup by `operation_id`. |
| `capabilities.read` | Secret-free manifest for the fixed environment. |
| `artifact.register` | Register a bounded content-addressed artifact. |
| `artifact.read` | Read one registered or permitted observation-referenced artifact. |
| `attempt.register` | Register immutable producer-neutral AttemptContext. |
| `injection.arm` | Arm a declared injection and record originating campaign/revision. |
| `injection.delete` | Delete one existing campaign injection and record its outcome. |
| `application.invoke` | Invoke one declared application operation. |
| `observation.read` | Collect an exact-invocation fixed permitted view or retrieve its receipt. |
| `observation.content.read` | Read at most 256 KiB of receipt-scoped permitted bytes with explicit availability and truncation. |
| `snapshot.create` | Planned target checkpoint within capacity; optional label/description and `maximum_committed_bytes`, with campaign ID from request/session, never failed-session continuation. |
| `session.stop` | Use `/v1/lifecycle` for permitted, confirmed target stop. |

Execution mutations require the same campaign and expected native session revision.
Worker ID and campaign revision are attribution only.
`close_execution` bypasses the revision check and running mutation queue, so
concurrent completion cannot prevent shutdown. Successful `session.owner` closure
MUST return the ExecutionOwner directly in the standard response `body` for both
live and retained stopped/error sessions, preserving original attribution and
closure state. Retained confirmation requires an already-recorded `closed_at`;
unconfirmed native closure returns `409 closure_unconfirmed`. The distinct
`session.status` response retains its nested `owner` field.
The explicit local administrator stop command closes admission; Operator must use typed `session.stop` and must
not fall back to the administrator command to bypass its recorded stop policy.
Read-only reporting and bounded finalization use the configured session scope.
Restore, confirmed stop and protected evidence export are provided by the same
integrated local service. Initial preparation/sealing/image construction and
administrator evaluation remain host CLI operations. Campaign checkpoint
inventory/inspection use the integrated `/v1/snapshots/list` and
`/v1/snapshots/inspect` routes, including retained earlier sessions.
Native target snapshots/restore are retained as experiment features: they capture
target state, not harness context. A planned restore is allowed only from a
healthy campaign at a quiescent boundary with known operation outcomes. It creates
a fresh Interceptor target session with existing `restored_from` ancestry while
the same Operator harness remains alive with its conversation, hypotheses, scratch
and pipes. Operator durably records the new binding/revision and returns it to
that live harness before further dispatch. Known preflight rejection leaves the
old target/harness/revision usable; post-closure failure or uncertainty is terminal.
It cannot resume a failed campaign or recreate harness context from a checkpoint.

At campaign execution end, Operator closes experiment admission and performs bounded
residual-injection cleanup under the same campaign, regardless of creator worker/revision. Deletion cannot
undo fidelity writes or application effects. Already-stopped targets are not
restarted for cleanup. Failed/unknown cleanup is reported and does not delay
guest destruction or cause experimental continuation. A user-attached target is
stopped only when that option was explicitly selected. Later authorized cleanup
or evidence collection may finish outstanding finalization without reopening
execution; unknown outcomes never authorize a guessed mutation replay.

### 13.5 Transport and availability

All public integration routes bind to `127.0.0.1:8080`. The service retains native
private file-spool or Unix transport to the network-disabled target. No extra
application/control HTTP listeners are exposed by integrated `run`.

Restore/stop admission and results are fsynced in a bounded host instance ledger;
exact retries return the original result or in-progress status, including across
session replacement. Experiments retain their separate native v1alpha2 records.
A lost response is reconciled under its original ID; never invent a fresh ID to
repeat an uncertain effect. Restore stops the old target before starting the new
one. Failure after closure is terminal and cannot authorize another experiment.

The host service itself owns the API, provider bridge and target lifecycle.
There is no independent gateway or gateway replacement protocol. Host-service,
controller/worker, guest or target failure ends execution. A restarted native
supervisor closes an old owner. Operator destroys the harness and reports
unconfirmed closure/results. Saved running records are audit evidence, not a
restart plan. Remote transport, authentication and multi-instance deployment are
deferred beyond this MVP.

### 13.6 Post-run export boundary

After target stop, the same host API remains alive for `/v1/status` and
`/v1/evidence`. Both source and restored session exports are accessible only under
the bound campaign. Export verifies native journals and streams bounded archive
data without accepting a caller host path. Operator verifies hashes, records
partial/missing outcomes and binds each native session to its campaign revision;
the harness never receives protected evidence. Optional final target shutdown
remains governed by the attach policy. Ctrl+C ends the service and remaining
target; later administrator CLI export is available from retained records.

## 14. INT-AEF-AD-011 — extended native model providers

**Implementation status:** supported alongside OpenAI Chat Completions, OpenAI
Responses, Bedrock Converse, and LiteLLM. The native, like-for-like providers
are:

| Provider adapter | Application codec and route | Host behavior |
|---|---|---|
| `anthropic-messages` | `anthropic_messages`, `POST /v1/messages` | Fixed-origin Anthropic Messages request with host API key or configured workload token and pinned API version. |
| `gemini-api` | `google_generate_content`, Gemini `models/{model}:generateContent` | Fixed Gemini Developer API origin with host `x-goog-api-key`. |
| `vertex-gemini` | `google_generate_content`, Vertex publisher-model `generateContent` | Fixed Google Cloud project, location, publisher, API version, and host ADC/workload identity. |
| `azure-openai` | Existing `openai_chat_completions` and `openai_responses` codecs under `/openai/v1` | Fixed Azure OpenAI/Foundry resource with host API key or Entra workload identity. |

The local application proxy accepts the native route needed by its SDK, checks
an exact model or Azure deployment allowlist, and sends the unchanged native
semantic shape to the compatible host adapter. It does not translate Anthropic,
Google, OpenAI, or Bedrock conversations into another provider's protocol.
Incompatible codec/provider pairs fail explicitly.

The application may receive declared synthetic SDK credentials that are valid
only for Interceptor's reserved `model-proxy`. The proxy ignores and strips
them. Real API keys, cloud credentials, acquired OAuth tokens, Anthropic API
versions, Google project/location, Azure resource origins, and provider routing
remain host configuration and never enter the Blueprint, container, snapshot,
evidence body, or exported artifact.

The first slice supports non-streaming text, system instructions, bounded
generation parameters, structured text/JSON output, and client-side function
declarations, calls, and results. Client functions remain application-executed;
the model provider only returns structured data. Reject streaming, embeddings,
image/audio/video/document blocks, file or remote-URL references, cached or
provider-stored conversation dependencies, background/batch operations,
Anthropic server tools, Gemini grounding or code execution, and Azure/OpenAI
hosted tools.

Provider configuration and validation requirements are:

- fixed HTTP origins reject user information, fragments, caller-supplied query
  strings, and cross-origin redirects;
- Anthropic pins the required API version and rejects undeclared beta headers;
- Gemini constructs its model path from an exact allowlist and accepts no guest
  destination;
- Vertex fixes project, location, publisher `google`, API origin, and version;
- Azure uses the configured `/openai/v1` resource origin and treats `model` as
  an exact deployment allowlist value; and
- all adapters retain existing body, timeout, concurrency, session, and
  provider-error bounds.

CapabilityManifest reports provider kinds, compatible codecs, authentication
mode classes without credential identifiers, model-ID constraints, and feature
flags for text, client functions, structured output, streaming, embeddings,
multimodal content, provider-hosted tools, and provider-stored state.

Evidence records application codec, selected host adapter, exact model or
deployment, pinned non-secret endpoint/API-version metadata, final injected
application request, canonical provider request and response digests,
normalized usage, latency, finish/safety status, bounded provider error, and
injection lineage. Authentication headers, credentials, access tokens, signed
cloud requests, and synthetic credential values are excluded.

## 15. INT-AEF-AD-012 — host secret-store credential resolution

**Implementation status:** supported. A shared host credential resolver covers
AWS Secrets Manager, Azure Key Vault, Google Cloud Secret Manager, and
HashiCorp Vault KV v2. Direct workload identity remains available for Bedrock,
Vertex Gemini, and Azure OpenAI.

Add one host-only credential resolver used by model-provider adapters and any
future trusted controller integration that requires an API key or client
secret. Provider adapters consume a resolved bounded value; they do not each
implement a secret-store client. Workload-identity model authentication such as
Bedrock roles, Vertex identity, or Azure managed identity remains direct and
does not create a needless stored secret.

Schema: `interceptor.dev/host-credential-ref/v1alpha1`

Store profile schema: `interceptor.dev/secret-store-profile/v1alpha1`. It binds
a stable profile ID to exactly one backend kind, production authentication
mode, cloud/region or Vault origin and TLS policy, allowed locator prefixes,
request timeouts, value-size ceiling, and cache-TTL ceiling. It contains no
secret value or static cloud access credential.

```json
{
  "api_version": "interceptor.dev/host-credential-ref/v1alpha1",
  "kind": "HostCredentialRef",
  "credential_id": "target-openai-key",
  "store_profile_id": "production-gcp-secrets",
  "locator": {
    "backend_kind": "gcp-secret-manager",
    "project": "security-simulation-prod",
    "secret": "interceptor-openai",
    "version": "latest"
  },
  "value": {
    "format": "json-string-field",
    "field": "api_key"
  },
  "cache_ttl_seconds": 300
}
```

`HostCredentialRef` and its `SecretStoreProfile` are permission-restricted host
controller configuration. Environment Blueprints, Operations requests, execution
session bindings, applications, and harnesses refer to neither a store nor a locator. A
reviewed model-provider profile may refer only to the stable `credential_id`.
Untrusted input cannot replace the backend, secret name, version, JSON field,
endpoint, trust root, project, vault, region, namespace, or authentication mode.

The initial backend union is:

| `backend_kind` | Read operation and strict locator | Production bootstrap authentication |
|---|---|---|
| `aws-secrets-manager` | `GetSecretValue` for one exact secret ARN or name, region, and optional version ID or stage | Workload/instance/container role, explicit AWS named profile, or explicit AWS environment identity |
| `azure-key-vault` | `GetSecret` for one exact HTTPS vault origin, secret name, and optional version | Explicit workload identity, managed identity, Azure CLI login or client-secret service principal |
| `gcp-secret-manager` | `AccessSecretVersion` for one exact project, secret, and numeric version or reviewed alias | Workload Identity Federation, attached service account, or explicit local/service-account Google ADC |
| `hashicorp-vault` | Read one exact KV v2 namespace, mount, path, version, and field from a fixed HTTPS origin | Vault Agent or Vault Proxy owns environment-appropriate auto-auth and renewal; Interceptor uses a protected token sink or fixed local authenticated proxy |

Cloud stores use official SDK endpoint resolution for the configured cloud and
region; arbitrary endpoint overrides are rejected in production. Private
endpoints use trusted DNS and network policy. Vault profiles pin the exact
origin, namespace, TLS roots, and allowed KV mount/path prefixes. Production
profiles never disable TLS validation.

The resolver exposes read only. It cannot create, update, rotate, list, or
delete secrets, and its bootstrap identity receives only per-secret read
permissions. Cloud stores MUST support the explicit bootstrap selectors in
[host authentication](../docs/cloud-authentication.md), independently of model authentication. Vault delegates
its many platform authentication methods to the separately administered Agent
or Proxy rather than reimplementing them in Interceptor.

Values are limited to a bounded UTF-8 string or a named top-level JSON string
field. Binary blobs, templates, commands, recursive references, and expression
evaluation are rejected. Provider-returned integrity data, including Google
Secret Manager CRC32C, is verified when available. The controller records only
the credential ID, backend profile ID, opaque provider version, resolution
time, and outcome in protected audit state. It never records the locator,
secret value, authentication material, or an unkeyed secret digest.

Resolve before the first dependent operation and retain the value only in a
bounded host-memory cache. Invalidate it at its configured TTL, on explicit
administrative reload, or after an authentication failure. Rotation may be
observed at the next resolution boundary, while one in-flight request retains
one immutable value. Disable credential-bearing core dumps, centrally redact
errors and telemetry, and fail closed on store outage, authorization failure,
disabled versions, malformed values, excess size, or TLS failure.

Model keys SHOULD use a host secret store. Explicit `--provider-auth api-key-env`
with a named `--model-api-key-env` MUST also be supported in production and
foreground/service modes. The implicit environment compatibility path remains
nonproduction-only. Secret values are never accepted through a Blueprint, CLI
argument, session API, Operations request, or inline controller profile.

Secret-store configuration and credential bindings are not target capabilities.
`CapabilityManifest` and `EvidenceBundle` omit configured backend kinds,
locations, paths, account/project/vault identifiers, secret versions, and
resolution events. Product release compatibility metadata may declare which
built-in resolver backends are present without revealing deployment
configuration. Runtime-loaded secret resolver plugins are not permitted.

## 18. Acceptance criteria

- A non-AEF harness can discover capabilities, register a payload and attempt,
  execute it, receive permitted feedback, and export evidence.
- Operator can execute an AEF-planned scenario without sending AEF-specific
  technique fields to Interceptor.
- Every relevant protected event correlates to attempt and verified payload
  digest where causality is known.
- A black-box engine cannot obtain raw oracle, fixture, canary, event, or
  provider-boundary details.
- A trusted post-run exporter obtains complete or explicitly partial evidence
  after live authority closes.
- Capability manifests are deterministic and secret-free.
- Operations requests cannot acquire Docker, host filesystem, generic proxy,
  shell, arbitrary URL, or private bridge authority.
- Different campaigns, closed execution, stale native state revisions, changed command under an
  identity, excess native limits and cross-session requests fail closed. Concurrent
  live duplicates do not create additional effects.
- Session campaign association is atomic and immutable; closing execution is irreversible
  across request retries. A failed execution cannot be resumed by restarting a
  controller/service or replaying recorded operations. Healthy planned restore
  creates a fresh native session under the same campaign.
- Event/state journals, attempt/artifact records and evidence export retain
  attribution and explicit partial/unknown outcomes after failure.
- Residual cleanup remains bounded and attributable. Failure never delays guest
  teardown, fabricates a clean result or reopens experimental execution.
- Supervisor limits, unexpected exits and connector failures promptly publish durable
  error/closed status with the original session/reason/time. Planned stops/restores,
  failed preflight races, replacement startup races, stale callbacks and failed
  persistence cannot produce a false healthy status or block Docker termination.
- Snapshot and restore actions require Operator control, preserve
  content-addressed lineage, enforce local and Operator-held cumulative limits
  across planned target-state revisions, and appear in protected evidence.
- An engine can at most request a permitted snapshot action and cannot obtain
  snapshot bytes, unrelated inventory, cross-campaign restore, or an
  administrative credential.
- AD-006 and AD-007 tests prove the new ingress positions are distinct from
  existing request-side and model-boundary injection.
- AD-011 tests complete non-streaming text and client-function round trips for
  Anthropic Messages, Gemini Developer API, Vertex Gemini, and Azure OpenAI
  Chat/Responses using only host credentials and like-for-like codecs.
- Unsupported provider/codec pairings, unallowlisted models/deployments,
  caller-selected routing, cross-origin redirects, unknown native fields,
  streaming, embeddings, multimodal content, provider-hosted tools, files, and
  background operations fail before provider contact.
- Each supported secret-store backend resolves an exact allowlisted credential
  using its production workload-identity or Vault auto-auth path without a
  plaintext secret environment variable.
- Caller-supplied locators, unapproved origins, missing or disabled versions,
  malformed or oversized values, integrity failures, and store outages fail
  closed without starting a dependent session or disclosing secret material.
- Rotation is observed only at a defined resolution boundary; protected audit
  records identify the credential binding and opaque backend version without
  storing a locator, value, or unkeyed digest.
- Production mode MUST permit explicitly selected host environment credentials.
  It MUST reject secret values in CLI arguments, Blueprints, session APIs and
  Operations messages; environment key lookup MUST use `api-key-env`.

### Campaign checkpoint metadata acceptance (2026-09-16)

Creation, CLI JSON output and local list/inspect preserve hash-covered campaign
ID and optional description. Description is bounded to 4,096 UTF-8 bytes. Native
creation derives campaign ID from the associated request, never a body override.
Campaign inventory includes earlier retained sessions after repeated restores and
remains readable after stop without target restart. Wrong-campaign/source reads,
corrupt metadata and limit overruns fail explicitly. Healthy target restore
preserves the live harness context; only its active target binding/revision changes.
See the normative [local API contract](../docs/local-api.md#snapshot-inventory-and-metadata).

### Snapshot caller byte allowance

The closed `snapshot.create` body accepts optional `maximum_committed_bytes`, a
nonnegative signed 64-bit JSON integer. Null, negative, fractional, string and
out-of-range values are invalid. Omission selects the native remaining allowance;
explicit zero is exhausted. The private snapshot API and standalone CLI
`--maximum-committed-bytes` have the same semantics. Campaign ID remains bound
from the operation envelope, not a body override.

Under the exclusive snapshot/control and activity locks, compute the native
remaining allowance as `min(16 TiB, max_blob_bytes * max_snapshots)` minus native
consumed snapshot bytes, saturating safely and treating zero/negative remaining
as exhausted. If supplied, the caller allowance can only reduce that value.
After the final stable filesystem scan, sum canonical file sizes and reject any
candidate exceeding the effective allowance before filesystem-delta/snapshot-state
commitment or checkpoint publication. Equality is allowed. Exhaustion returns
`429 snapshot_bytes_exhausted`, with no checkpoint or snapshot counter charge and
no terminal closure of a healthy target. Scanning may stage blobs; this allowance
limits checkpoint commitment, not all temporary disk writes.

Operator always supplies its remaining campaign allowance (default cumulative
budget 1 GiB), with a separate default 20 creation admissions. Those campaign
counters do not rewind when native counters are restored; Interceptor does not
maintain Operator's campaign ledger. Native snapshot count limits remain in force.
The supplied field is covered by the body digest and operation identity. Retry
with the same operation ID and unchanged body/envelope returns the saved result
without a second checkpoint/charge; changing the allowance conflicts. Reconcile
unknown outcomes using that original operation rather than issuing a fresh one.

### Operator attempt numbering and loop accounting

Operator/Attack Harness use the [shared campaign allocator and loop rules](../../operator_sandbox/schemas/HARNESS_EXECUTION_RULES.md).
An allocated rejected submission keeps its attempt_index; a corrected submission
uses fresh IDs and a higher index. Gaps are valid, and healthy restore never resets
Operator's campaign high-water mark or admission budget. Operator sends the index
unchanged to native AttemptContext. Interceptor requires an index greater than the
highest currently registered index, not the next consecutive integer. It limits
the number of registered attempts, not their index values. A rejected registration
adds no native entry. Native registry state can rewind on restore; cumulative
campaign enforcement stays in Operator and the continuing harness. Exact native
operation retries use the existing durable operation ID/body and saved result.
No Interceptor RPC, ownership check or native attempt version change is introduced
for harness-local numbering or loop limits.


### Execution and identity alignment

Interceptor MUST default to foreground `run` and MAY use the same command under
an explicitly installed, non-restarting systemd/LaunchAgent service. Both modes
MUST use identical credentials and lifecycle semantics; a service has its own
configured account/environment. The [shared host authentication contract](../docs/cloud-authentication.md)
is authoritative for model and store selectors, portable credential files,
GitHub OIDC bootstrap, required model/secret permissions and renewal limits.
